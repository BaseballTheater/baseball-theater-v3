# Run stories

The owner's shorthand (2026-10-30): _"loop the next 10 stories, in order, and if you get blocked, move on to the next story that has no unresolved dependencies."_ This skill strings together the flow `CLAUDE.md` already defines for one story — it adds no new rules and relaxes none.

**This thread coordinates; each story runs in its own fresh-context subagent** (owner, 2026-11-04: "All 3", to running each story in a fresh-context subagent among the token cuts). Before this, one context carried every story: 92% of a run's input tokens, a median of 200–300k tokens re-sent on every request, because whatever one story read stayed for all the later ones. Here the coordinator keeps only what it needs to choose and check stories: the gate scripts, `docs/v3/INDEX.md`'s story list, `git`, and each worker's short report. **Don't read story notes, code, skills or ledger entries in this thread** beyond the frontmatter eligibility needs; the workers and review subagents read them.

**Argument:** `N`, the number of stories to **start** (default 10). Count starts, not finishes, so a run of parked stories can't stretch the loop past what the owner expected. Resuming a story that was already `doing` or `blocked` (step 1) does not count.

## 0. Before the first story

- `git status`: if a finished story is uncommitted, commit it first (rule 6). If uncommitted work you can't attribute to a story is in the tree, stop and ask. (`docs/v3/.obsidian/workspace.json` is editor state — leave it out of commits, ignore it.)
- A story already `doing` that waits on the owner (e.g. a design match): park it as in step 4 before moving on. One that is mid-build: finish it first, as step 3.
- `git fetch origin`: the run's first story branches from `origin/stage` (step 3).
- The agent types this skill names (`story-worker`, `pre-pr-reviewer`, `db-reviewer`, `fix-worker`, `fix-plan-reviewer`, `arbiter`, `backlog-reviewer`, `design-intake-reviewer`, `design-intake-merger`, `doc-parity-reviewer`) live in `.claude/agents/` and load only in a session started after that directory exists: if the Agent tool doesn't list them, restart the session before the first story.

## 1. Owner answers first

If the owner has, **in this session**, answered a parked story's question (a design match "Yes", a ratification go-ahead, a fence or scope decision), finish that story before starting new ones: hand it to a worker (step 3) with the owner's words quoted **verbatim** in the brief, to apply (e.g. `scripts/audit.sh story <ID> --design-match -` with those words) and then finish the story. Never infer an answer — no explicit owner words in this session, no change.

## 2. Gates, before every story

Check in this order:

1. **Backlog review due?** `scripts/review-debt.sh` counts `done` flips since the last review (6 triggers it) and the drift events git records; add any it can't see (`CLAUDE.md` → Agent / loop rules). Don't read `docs/v3/AUDIT.md` to count — it is ~1 MB. If due, run `.claude/skills/backlog-review/SKILL.md` in a **fresh-context subagent** (the Agent tool, `subagent_type: "backlog-reviewer"`, which loads the skill itself; this skill is the owner's explicit request for it — the agent that built the stories must not review them). Give it the script's output; **don't read the skill into this thread** (it is ~12 KB and was being pasted into the coordinator's context on every review). It makes its edits, logs them with `scripts/audit.sh review` and commits; check the commit landed. A design intake (the script says when) is two `design-intake-reviewer` subagents, started at once, each loading `.claude/skills/design-intake-review/SKILL.md` itself; then one `design-intake-merger` subagent, given both reports, merges, applies, logs and commits, so the merge also happens outside this thread.
2. **Doc parity due?** `pnpm parity:debt`. If due, run `.claude/skills/doc-parity-review/SKILL.md` the same way, in a `doc-parity-reviewer` subagent.
3. A review verdict of **`blocked` stops the whole loop** — go to step 5. Questions from a `continue` / `amended` review don't stop it; collect them for the summary.

## 3. Pick and run the next story

**Eligible** = the lowest-`priority` story with `status: todo` whose:

- every `depends_on` story is `done` (a dependency that is `doing`, `blocked` or `todo` is unresolved — e.g. S67 waits while S66 waits on a design match);
- every `design:` story is `done` (rule 18);
- it is not a story this run held (`docs/v3/LOOP.md` §7 step 3, "Exit"): its note on the current branch still reads `todo`, but its work sits on its own unpushed branch, so it is never picked again.

Read both lists from the note's frontmatter in `docs/v3/backlog/stories/S<N>.md`. The generated **Next** line in `BACKLOG.md` checks designs only, not `depends_on`, so don't rely on it alone. `superseded` stories are skipped.

Find it from the **Stories** section of `docs/v3/INDEX.md` (open stories with their `depends_on` and design lists, then the `done` ones) or the notes' frontmatter; nothing else is needed to choose.

**Give it its own branch first** (S121; owner, 2026-11-07: "I want a release to be a set of PRs basically"): `git switch -c story/S<N>` from `origin/stage` for the run's first story, and from the previous story's branch for each later one (skipping any story its fix loop's arbiter held, `docs/v3/LOOP.md` §7 step 3, "Exit": then from the nearest earlier story that isn't held, or `origin/stage`), so a run's stories stack and each branch holds its story and the ones before it. The worker commits there; nothing is committed on `stage` itself.

**Hand the story to a worker:** one fresh-context `story-worker` subagent per story (the Agent tool, `subagent_type: "story-worker"`, `run_in_background: false`: the next story waits on this one's commit; `.claude/agents/story-worker.md` carries the worker's standing rules, and the brief below still goes in full). Workers run one at a time, never in parallel: they share the working tree. The brief is self-contained, since the worker starts with none of this thread's context:

> Run `/goal S<N> done` exactly as `CLAUDE.md` → "`/goal <ID> done` shorthand" defines it, as one step of `/run-stories` (`.claude/skills/run-stories/SKILL.md`, steps 3–4): quote the `/goal` line and ACs word for word, `status: doing` + `pnpm backlog:build`, the reuse check, grader written and shown red on HEAD before product code, build inside the fence, grader green, `pnpm verify` 0, `status: done`, `CHANGELOG.md`, the baseline table (rule 17), `scripts/audit.sh story S<N>`, one commit. Start from `docs/v3/INDEX.md`. Do not push, start another story, or run a review. If the story is blocked (step 4's list), park it as step 4 says and stop. [Owner's answers for this story, quoted verbatim, if any.]
>
> Reply with only: **outcome** (`done` or `parked`); the **commit** sha; a **one-line impact**; your `Goal for S<N>:` quote and your `S<N> verified:` section exactly as you wrote them; and, if parked, **each question for the owner**, written as step 5 asks (bold direct question first, then self-contained context), plus any drift event (turn cap, fence).

When it returns, check rather than trust: `git status` is clean, `git log -1` is the commit it named, and the note's `status` is `done` or `blocked`. If not, finish or park the story yourself from what is committed, and say so. **Then, before the next story branches from this one, run its pre-PR review** (`docs/v3/LOOP.md` §7 step 2): parallel fresh-context `pre-pr-reviewer` subagents, one per checklist slice, each given §7, its slice and this story's own diff (`git diff <base>...story/S<N>`, where `<base>` is the branch it was cut from, or `origin/stage` for the first, after `git fetch origin`). When that diff touches the database paths §7 step 2 lists (the schema, migrations, the classification manifest, repositories or any SQL), start one `db-reviewer` beside them (owner, 2026-11-13: "we need an agent that is a database specialist reviewer whose job it is to examine the DB schemas and queries we establish"), limited to those changes (owner, same day: "the DB reviewer's reviews should be limited to JUST changes that impact the database queries and schemas, but it will need the context about why those changes are made"): give it that slice of the diff, the story's note path (its ACs say why) and the owner's quoted decisions for it. Its must-fix findings join the merged report; its forward-looking ones go in the run summary for the owner and never hold the story. Merge their reports and drop duplicates. The goal is that Claude's review finds nothing (owner, 2026-11-07, of Copilot's review, which Claude's replaced on 2026-11-11: "Our goal should be zero Copilot discoveries for each pull request"). If they find anything, fix it as §7 step 3 says: one fresh-context `fix-worker` (this thread doesn't read code) gets every merged finding and plans the fixes, a fresh-context `fix-plan-reviewer` checks the plan, the worker builds it uncommitted on `story/S<N>`, and a fresh-context `pre-pr-reviewer` (on the same model tiers as the pre-PR review) checks those changes (new files included) plus every caller they affect, with a `db-reviewer` beside it when the fix touches those database paths, repeating until they find none. This thread runs each round and passes the plan and verdicts between subagents, and after three rounds or a repeated finding hands the open findings to a fresh-context `arbiter`, which clears them, holds the story (its uncommitted fix work thrown away, its branch left unpushed), or escalates a call it judges too impactful to make to the owner (§7 step 3, "Exit"). Only then does the worker run `pnpm verify` (a change made to get it green goes back for review), re-run `scripts/audit.sh story S<N>` for a `done` story so the ledger names the commit that ships (a parked checkpoint keeps no ledger entry until it's finished: `audit.sh` writes a "completed" entry whatever the grader says), and make one commit. Only then does the next story branch from it. Relay the worker's `Goal for S<N>:` quote and `S<N> verified:` section to the owner as they are (the `/goal` rule asks for both); keep any questions for the summary. Don't push per story: the run pushes once, at the end (step 5), as one pull request per story.

Give the owner a one-line progress note when each story starts and ends.

## 4. Blocked → park and move on

A story is **blocked** when it needs something only the owner can give, or the rules forbid going further:

- a design match (rule 22) or ratification (rule 18) waiting on the owner;
- an AC that can't be met inside the fence (rule 10) — never widen it;
- a missing input the story says to stop and ask for;
- the turn cap reached;
- an owner decision the story can't make (a pillar citation, an `Open:` source, a new ADR).

The worker parks it (and the coordinator, if a worker stops without doing so):

1. Commit everything done so far, on the story's `story/S<N>` branch, as a **checkpoint** (grader, code, captures), worded like earlier checkpoints: `S<N> checkpoint (parked for …): …`. `pnpm verify` must exit 0 at the checkpoint. If it doesn't and can't be made to inside the fence, revert the story's product changes, keep the grader, and say so.
2. Set `status: blocked` in its note, `pnpm backlog:build`, include it in that commit. A committed checkpoint satisfies rule 6, so other stories may run.
3. Record the question for the summary (what it needs, with the evidence). For a design match, run `pnpm design:review <ID>` and name `.designreview/<ID>/`; run `pnpm design:review <ID> --done` once the owner gives the verdict.
4. A turn-cap hit or a fence problem is a **drift event**: the next step 2 makes a backlog review due.

Then go back to step 2.

## 5. Stop

Stop when `N` stories have been started, nothing is eligible, a review returns `blocked`, `pnpm verify` breaks in a way no story owns, or the owner interrupts. A story its fix loop's arbiter held (§7 step 3, "Exit") is not pushed or opened as a pull request; the stories started after it were cut past it (step 3), so they push as usual. If the arbiter holds a story during step 2 below, while Claude's review comments are being fixed, its pull request keeps auto-merge off with a comment naming the open finding; the branches stacked on it that aren't pushed yet stay unpushed until it is fixed, and any that already have a pull request keep auto-merge off, each with a comment naming that open finding, until the fix is merged forward into it and Claude's review of its new head is handled (step 2). The summary lists each held story and every branch waiting on it. Then push once, for the whole run (owner, 2026-11-02: "if we're using run-stories, we don't have to push until they are all done"), as one pull request per story into `stage` (S121; owner, 2026-11-07: "I think releases to main probably should use GitHub releases, if that's actually possible. I want a release to be a set of PRs basically", and on who merges them: "1. You automatically"):

1. Check GitHub Actions on `stage` first (`gh run list --branch stage --limit 1`), as `CLAUDE.md` → Agent / loop rules says.
2. In story order, for each `story/S<N>` branch (done or parked checkpoint): its pre-PR review already ran in step 3 (below "When it returns"), before the next story branched from it, so its pre-PR fixes are already in every later branch. Then `git push -u origin story/S<N>`, `gh pr create --base stage --head story/S<N> --title "S<N>: <one-line impact>" --fill`. Wait for Claude's review (`.github/workflows/claude-review.yml`) and handle every comment before turning on auto-merge (`gh pr merge --auto --merge story/S<N>`), as `CLAUDE.md` → "Claude's review is handled before a pull request merges" says (owner, 2026-11-07, of Copilot's review, whose rule Claude's kept on 2026-11-11: "If Copilot continues giving the same feedback you can merge when you feel the real stuff is all handled"); a fix goes on that story's branch through `docs/v3/LOOP.md` §7 step 3's fix flow (3.1–3.5, as step 3 here describes), and a comment that isn't real gets a reply. The moment a real finding of Claude's review, or a failed check, arrives on `story/S<N>`, auto-merge is turned off on every open pull request stacked on it (`gh pr merge --disable-auto story/S<M>`), since each carries `story/S<N>`'s code and merging it would land that finding in `stage` and mark `story/S<N>`'s pull request merged; it stays off until the fix is merged forward into that branch and Claude's review of its new head is handled. A fix committed on `story/S<N>` after a later story branched from it (for Claude's review here, or for a failed check in step 3) is merged forward, in story order, into each later stacked branch, each branch from the one it was cut from (`git switch story/S<M> && git merge --no-commit --no-ff story/S<previous>`, where `story/S<previous>` is the branch `story/S<M>` was cut from, so a conflict is resolved once and carried down the stack); never a rebase or force-push, so pushed shas and ledger commits stay valid. A conflict in `docs/v3/AUDIT.md` keeps both sides' entries whole, the earlier story's first; any other conflict (`CHANGELOG.md`, the Current baseline frame note) keeps both stories' changes, the earlier story's first, and the baseline's **As of** line is the later story's; `docs/v3/audit.jsonl`, `docs/v3/INDEX.md` and `docs/v3/BACKLOG.md` are regenerated with `pnpm backlog:build`, never hand-merged. `--no-commit` stops even a clean merge before it commits, so `pnpm backlog:build` and `pnpm verify` run on the merged tree first; then `git add` the resolved and regenerated files, and only then `git commit`. A merged branch with no pull request yet is not pushed then: it is pushed only when its own turn in this step comes, so a story held later still leaves it unpushed. A merged branch that already has a pull request (its auto-merge already off, as above) is pushed, and waits for Claude's review of its new head, handled as above, before auto-merge goes back on. A review run that fails is re-run; a pull request never merges without a finished review of its newest commit, and if the review still can't run, the run stops and asks the owner. Auto-merge merges each pull request once its required checks (`ci-passed`) pass. Because the branches stack, a later pull request also carries the earlier stories until those merge; GitHub marks an earlier one merged if a later one lands first.
3. Watch the pull requests' checks (`gh pr checks <number> --watch`, in the background) and report each one's result in the summary; a failure is the next thing to fix, committed on that story's branch, and merged forward into every branch stacked on it as step 2 says.
4. Once they merge, bring the local `stage` up to date (`git fetch origin && git switch stage && git merge --ff-only origin/stage`).

Each pull request is assigned to the next release's milestone when it's opened, and a story counts as complete only once that release is published; the summary says which release each story waits for. A run never pushes directly to `stage` or `main`, never merges into `main`, and never prepares or publishes a release on its own: the coordinator prepares one (a checked draft) and later publishes it, each only when the owner says so, publishing drafts in version order; production refuses a release lower than one already published, and rolls back only by re-running an earlier released version's Deploy run (`CLAUDE.md` → "The coordinator manages releases"; owner, 2026-11-07: "I want you to manage the releases"; then "Release when I say so. PRs must be assigned a release to be considered complete, and PRs cannot be merged to main with no release. Roll back on your own. v3.0.0. I keep DNS cutover."). Never deploy by hand.

End with one summary:

- **Done:** each story with its commit and a one-line impact.
- **Parked:** each `blocked` story, what it waits on.
- **Questions for the owner**, every one from stories and reviews, numbered, each a **bold direct question first**, then self-contained context (no "see above"). The context never stops at an ID or an AC number (owner, 2026-10-30: "you need to tell me more than just the label for the AC or the Story"): say what the story builds, what the AC or change says in plain words, what went wrong or changed, and what each answer would lead to.
- **Database, for later:** each `db-reviewer` forward-looking point, with the story it came from and the feature or story it serves; ask whether to file it as an issue.
- **Not eligible:** stories skipped, and the unresolved dependency or design for each.
- **Next run:** what `/run-stories` would pick up first.
