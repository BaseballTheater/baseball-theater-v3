# A9 — The changelist page, and what's new on the update notices (S133)

Amends the ratified [shell-scoreboard design](../DESIGN.md) (ratified 2026-10-14) and its amendments [A1](A1.md)–[A8](A8.md). Story **S133**; built by S134 (the page) and S135 (the notices and the version line). **Draft, not ratified.**

**Adds:** a "What's new" page that lists every release's approved notes (S131's `ReleaseNotes`, served by S132's `GET /api/v1/releases`), newest first, in S131's three buckets: the headline additions, each other item labeled by its kind, and the one "fixes and polish" line; with its empty, loading and error states. A "See what's new" link and the big additions on A6's update-available notice. An after-update notification that floats where A6 does, says which release the app now runs, shows that release's big additions and the link, and dismisses itself.
**Overrides:** A6's floating notice (drawn in words; the S28 and S73 captures are its record): a link sits at the left of its button row, and the big additions sit between its message and its buttons. The rail's version line in `scoreboard-header-version-desktop` (A5) and the drawer's (A2's `nav-drawer-mobile`, `-medium`) reads the build's release version once the build knows it.
**Repeals:** nothing.

Source: https://www.figma.com/design/wqGKEFlvyxq0ObWZhRJdPF — section "Z — Changelist and update notes (S133, awaiting ratification)", live file as edited in the S133 session (no named version).

In words, not drawn:

- The drawer on mobile and medium shows the same version line as the rail. A build that knows no release (none approved yet) keeps today's `v3.0.<Actions run> (<commit>)` line (S135 AC 4).
- Pending Q2: the version line, in the rail and the drawer, is also a link to the page; it looks as drawn (no underline until hovered or focused).
- A release with no date shows its version alone. Release notes carry no scores, so Hide Scores changes nothing on the page or the notices.
- When the after-update notification's request fails or returns no release, it shows the message and the link alone (`updated-notice-*`), as A6 shows its link alone (`update-notice-link-*`).
- The after-update notification is not drawn with the retired-version case: it appears only on a fresh load of a newer build, which is not retired.

## Decisions

Recorded as the owner stated them.

- The page and the notices (owner, 2026-11-08): "I need a user-facing changelist page which lists the changes in each release simplified to just those things which impact users. Minor bugs and fixes should fall into a single bucket. Others that are either very impactful bug fixes, new settings, new features, new significant design changes, etc should get their own items. The update dialog should link to it and a notification that auto dismisses after updating should show a link to it. Really big new additions should show on the update notification itself (via API data comparing versions)."
- Which notification shows the big additions (owner, 2026-11-08, asked which notification): "Both"
- Where the page starts (owner, 2026-11-08): "No, start at v3.1.0"
- The rail's version line (owner, 2026-11-08, asked whether the rail shows the release or stays a build counter): "Follow semver"

- *Agent:* pending Q2: the page is reached from the two notices' links and from the version line at the foot of the rail and the drawer; it is not added to the nav list. A signed-out visitor sees it too.

## Open questions

1. **Q1.** **Should the page live at `/whats-new` and be called "What's new"?** That is how it is drawn. The alternative is `/changelist` (or another address) and the title "Changelist".
2. **Q2.** **Should the page be reached only from the notices' links and the version line at the foot of the rail and drawer?** As drawn, it isn't in the nav list; tapping the version line opens it. Alternatives: add it to the nav list, or put a link in Settings.
3. **Q3.** **Should the after-update notification dismiss itself after 10 seconds?** The timer pauses while the pointer is over it or focus is inside it, and the `✕` closes it at once. Any other number of seconds works the same way.
4. **Q4.** **When the server has retired this version, should the update notice hide its link and show no additions?** That build can't load the notes (every route of its version answers 426), so its link would open the page's error state. As drawn, it shows only the message, Snooze and Update Now; after updating, the after-update notification gives the link. The alternative is to keep a link that runs Update Now first and opens the page once the new version has loaded.
5. **Q5.** **When the update notice is also up, should the after-update notification stack directly above it at the bottom?** As drawn, the update notice keeps the bottom and the after-update notification sits 8px above; the offline marker under the header stays where it is. The alternative is to show one at a time (the after-update notification first, the update notice after it dismisses).
6. **Q6.** **Should a notice show at most two big additions, then "+N more big additions"?** That keeps the box short on a phone. The alternative is a different cap, or every addition.
7. **Q7.** **Should the rail's version line keep the commit after the release version, `v3.2.0 (c46e853)`?** You already decided it shows the release version (Decisions); this asks only whether the commit stays beside it. The alternative is `v3.2.0` alone.
