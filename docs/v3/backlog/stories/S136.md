**Gap:** The owner wants the calendar to mark the days one of the fan's favorite teams plays (owner, 2026-11-09: *"If the user has >0 favorite teams, make the top right corner of the days at least one of their teams is playing. This means the API for that needs to return the teams that played each day."*). S124's month answer (`GET /api/v1/schedule/month/:month`; `ScheduleDayCount` in `packages/domain/src/schedule-month.ts`) gives each day's date and game count only, so the calendar couldn't tell which days those are without one schedule request per day.

**Impact:** Before S136, the calendar's data said how many games a day has but not who plays. S136 impact: the same one request also says which teams play each day, so S125's calendar can mark the days a fan's favorite teams play. One shared test also says whether a month has any games, for the calendar's off-season line.

**Notes:**

- **Why every team, not "does a favorite play".** Favorites are personal (`favoriteTeamIds` in the account's settings, `packages/domain/src/settings.ts`), and the month answer is cached for everyone by when the month last changed (S124 AC 3, ADR-021). Sending the day's teams keeps one shared, cacheable answer; the client compares them with the fan's favorites. A month is at most 31 days of about 30 IDs each (a few more on a day with exhibition opponents).
- **Where the teams are.** A stored schedule day's `games` are `ScheduleGameSummary` rows with `teams.away.id` and `teams.home.id` (`scoreboardRows` reads them, `packages/domain/src/scoreboard-rows.ts:30`). `PostgresScheduleRepository.listGameCounts` (`functions/src/adapters/postgres/repos.ts:95`) counts the games in the database so no document leaves it; read the IDs the same way (for example `jsonb_path_query_array` over `document`), and do the de-duplicating and sorting in one place both adapters share. `ScheduleDayTally` (`packages/domain/src/schedule-month.ts`) is the port's row and gains the IDs; `monthGameCounts` turns tallies into the answer's days.
- **Nothing special for unusual games.** The All-Star Game's two sides and an exhibition opponent have their own team IDs; they are listed like any other and simply never match a favorite.
- **Freshness is unchanged.** A day's `lastChangedAt` already moves when its games change (ADR-022), so the month's cache lifetime needs nothing new. An answer cached before S136 was deployed has no `teamIds` until it expires; AC 3's function reads that as no favorite playing, so the mark is missing for at most the cache's lifetime rather than the calendar breaking.
- **The favorite test already exists for a game.** `scoreboardRows` keeps a private `favorite(game)` test for one game's two teams (`packages/domain/src/scoreboard-rows.ts:30`). AC 3's function answers the same question for a day's IDs; leave `scoreboardRows`' behavior as it is.
- **Why the month test is here.** AC 4's function is the calendar's other derived value over the same month answer, and S125 can't add it (its fence is the web app). It reads S124's `ScheduleDayCount` rows and nothing else S136 adds, which is why the story's title doesn't name it.
- `web/src/api/generated.types.test.ts` lists each response type and `pnpm verify`'s drift gate (`web/src/api/codegen.test.ts`) re-renders `web/src/api/generated/` from the spec, as S124's note (c) says.
