**Gap:** MLB publishes the strike zone the ABS system judged a game against — its top and bottom as a share of the batter's height, and its width — through the live feed's `ruleSettings` hydrate; BT doesn't keep it (owner, 2026-10-30: *"Also add stories to ingest all of this extra data."*).

**Impact:** Before S100, BT drew the strike zone from each pitch's own top and bottom. S100 impact: BT keeps the zone the game's ABS challenges were actually judged against.

**Source:** Feature: More MLB game data

**Scope files:** `fixtures/`, `packages/mlb-api/src/`, `packages/ports/src/`, `packages/domain/src/`, `functions/src/`, `functions/vitest.config.ts`, `openapi/`, `docs/v3/BACKLOG.md`, `docs/v3/backlog/`, `docs/v3/AUDIT.md`, `CHANGELOG.md`

**Acceptance criteria** (checks `scripts/verify-S100.sh` performs)

1. `fixtures/raw/rulesettings-823823.json` holds MLB's response to `https://statsapi.mlb.com/api/v1.1/game/{gamePk}/feed/live?language=en&hydrate=ruleSettings&fields=gameData,ruleSettings` for 823823, recorded once with `BT_USE_LIVE_MLB=1` and committed; tests and local dev read it, never the network.
2. `packages/mlb-api` types the payload as named interfaces split by purpose and parses it with zod; a parse test runs on the recording, and `pnpm mlb:scan-drift` diffs it against the parser like the other payloads.
3. `MlbStatsClient` gains `fetchGameRuleSettings(gamePk)`, implemented by the fixture adapter and the HTTP adapter; ingest owns the call (ADR-002): no web code fetches it.
4. A mapper in `functions/src/mappers/` projects it into BT's own shape, `GameSnapshot.ruleSettings`, added to the game payload additively (regeneration test; `pnpm api:breaking` exits 0). Each setting by name with its value and unit; on 823823 `strikeZoneTopFactor` is 53.5% and `strikeZoneBottomFactor` 27% (test).
5. The source is optional: when the call fails or returns nothing, the field is absent and the game is served as before (test).
6. This file's S100 **Status** (story heading and top table) is `done`.
