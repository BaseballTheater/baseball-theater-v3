**Gap:** The change log page lists every release's approved notes (owner, 2026-11-08). The update-available notice was to show the big additions between the version a fan has and the one they're getting (owner, 2026-11-08: *"Really big new additions should show on the update notification itself (via API data comparing versions)"*), until the owner took the headline off it (2026-11-10: *"I didn't realize there would be a synchronization issue so I would rather not show the headline."*). Clients read only BT (ADR-002), and BT serves no release notes and doesn't say which release it is running.

**Impact:** Before S132, the app had no way to ask what changed between releases. S132 impact: one request gives every approved release's notes, so the change log page (S134) can show them.

3. The notes are bundled into the build from `releases/*.json` by one named command and parsed once with S131's parser; nothing reads the file system at request time, so the Worker serves them (a `*.workerd.test.ts` request returns them), and a build whose bundle is stale against `releases/` fails `pnpm verify` (drift test, as `web/src/api/codegen.test.ts` does for the generated client). The command refuses a file that doesn't parse or whose `version` doesn't match its file name, so two files can't claim one release (tests).
4. The response is cacheable for at most 5 minutes in all, `max-age`/`s-maxage` plus any `stale-while-revalidate` (`Cache-Control` header test), so a release's notes show within minutes of its deploy.
5. The route is in the OpenAPI spec (`pnpm api:spec`), `pnpm api:breaking` exits 0 (additive), and `web/src/api/client.ts` has one function for it, typed from the generated spec.
6. `CLAUDE.md`'s release rule (S131 AC 5) names AC 3's command as part of landing a release's notes, so the notes' pull request carries the regenerated bundle and doesn't fail the drift test (grep).
