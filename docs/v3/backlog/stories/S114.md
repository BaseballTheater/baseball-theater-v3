**Acceptance criteria** (checks `scripts/verify-S114.sh` performs)

1. A GitHub Actions workflow builds and runs `pnpm verify`, then deploys a preview Worker per pull request against the staging database (never production): previews and staging bind the same `bt-staging` Hyperdrive config on the Neon `staging` branch, which the workflow creates when it's missing (AC 5) (owner, 2026-11-05: "Previews share staging db"), and posts its address (workflow file; a dry run with `wrangler deploy --dry-run` in CI).
2. Every push to `main` deploys a staging Worker to `stage.baseball.theater` against a long-lived Neon `staging` branch (not production), with `pnpm db:migrate` run against that branch first (workflow file check).
3. Production deploys only from `main`, to `baseball.theater`, behind the GitHub environment `production` that requires the owner's approval; the workflow never deploys production without it (workflow file check).
4. Secrets (Cloudflare API token, Neon credentials) come from GitHub secrets, never the repo (grep).
5. Every deploy (preview, staging, production) runs `pnpm db:migrate` against its own database before the new Worker takes traffic, then `pnpm db:reapply-deletions` (S113), so a restored database never brings a deleted account back without anyone remembering a runbook step. Each environment's Hyperdrive config is found by its constant name (`bt-production`, `bt-staging`) and created only when missing, with its id resolved at deploy time rather than pasted into `wrangler.jsonc`, so production and staging share one code path. Every bootstrapping step the workflow performs (creating a Neon branch or Hyperdrive config, setting Worker secrets, migrating) is idempotent: running the same deploy again changes nothing and fails nothing (workflow check: each create step checks for what exists first). (Owner, 2026-11-05: "It should be idempotent so it can happen with every deployment. All the bootstrapping should be like that." It was "before the first production deploy".)
6. `README.md` documents previews, staging, releasing, rolling back (`wrangler rollback`), and the launch checklist the Later theme carries (legal check of ageing-out copies, `support@baseball.theater` routing, the R2 `ExportStore` and Cloudflare Email `Mailer` adapters) as items still to finish before a public launch.
7. No deployed environment (preview, staging, production) accepts a `dev:` sign-in: the Worker wires `DevIdentityProvider` only when `BT_LOCAL` is `"1"` (workerd test: `Bearer dev:test-user` is refused without it and accepted with it). (Added by the 2026-11-04 backlog review: `createWorkerApp` composes `createDevAuth`, whose provider list always has `dev`, `functions/src/adapters/fixtures/auth.ts:60`, `functions/src/services/accounts.ts:107`.)
8. Every deployed environment serves live MLB (`BT_USE_LIVE_MLB` is `"1"` in its `vars`), sets `BT_APP_ORIGIN` to its own address, and gets `BT_SESSION_KEY` from a Worker secret, never `vars` or the repo (`wrangler.jsonc` and workflow check). Every deploy pushes every Worker secret from GitHub secrets (idempotent), so GitHub is their one source and none is set once by hand with `wrangler secret put`. (Added by the 2026-11-04 backlog review: without the first the deploy serves the bundled fixtures, `createMlbClient` in `functions/src/worker-app.ts`; without the last each isolate signs sessions with its own random key.)
9. The staging branch never holds a fan's data: it's created schema-only (never a plain branch of production) and filled only by `pnpm db:migrate`, so no personal or deletion-log row is ever written to it (workflow check). Copying production's baseball data into it is **S117**, a step the owner runs by hand (owner, 2026-11-05: "Its own story, before production launch, but it should be a manual step (to allow for local iteration not getting stomped)"); no deploy copies data.

Staging needs its own config on the staging branch, and a per-PR branch needs one per preview (created and deleted by the workflow through the Cloudflare API, which needs the token's Hyperdrive edit permission) or previews share staging's. Which, and who creates `bt-staging`, is asked with this review.
- **Wrangler environments don't inherit bindings** (S113's note): `preview` and `staging` env blocks restate `hyperdrive`, `durable_objects` and `vars`, and each needs its own `routes` / custom domain (`stage.baseball.theater`, `baseball.theater`).
