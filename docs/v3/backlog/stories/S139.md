**Gap:** The owner wants Standings to show spring training, the regular season and the playoffs, one at a time with the fan able to switch (owner, 2026-11-10: *"I think the standings view should have an option. Basically, it should be capable of showing spring training, regular season, and playoffs."*), and wants the API to hand over every season phase's standings rather than know about those views (owner, 2026-11-13: *"I don't think we need the API to understand the "view" thing; it should categorize the results based on the season phase, and then return them all by default unless the API query specifies an "includePhases" query parameter"*; *"includePhases would be an array/comma-separated list of phase names"*). `GET /api/v1/standings` serves one table per day, the one `standingsPhase` picks (S128; `packages/domain/src/standings-phase.ts`, `functions/src/services/standings.ts`): in spring training there is no way to get the regular season's table, in the playoffs none to get the teams that made it, and nothing says when each phase starts and ends, which the page needs to choose what opens first (S130).

**Impact:** Before S139, the standings data was one table chosen by the calendar. S139 impact: one answer holds the day's spring training, regular season and playoffs standings, each with the days its phase runs, and a caller can ask for only some of them, so S130's page can offer the choice. Nothing on the page changes yet.

1. **The phases and the answer's shape.** The season phases are `spring`, `regularSeason` and `playoffs`, in that order: one exported type and one exported ordered list in `packages/domain`, beside `StandingsPhaseName` (`packages/domain/src/types.ts`), whose `spring` and `regularSeason` they reuse; `final` is not a season phase (it is the regular season's table after the regular season), and `playoffs` is new. `StandingsResponse` (`packages/domain/src/api-routes.ts`) keeps every field S128 serves with the same meaning (ADR-015: additive only), so a client that doesn't know phases (the page before S130, an installed app that hasn't updated) keeps getting S128's table, and gains `phases`: an object with a key for every phase, each value `{ startDate, endDate, table? }` or `null`. `startDate` and `endDate` (`string | null`) are the first and last day of that phase in the season the answer is for (AC 2), `YYYY-MM-DD`, both `null` only on the `regularSeason` phase of a day with no calendar for its season or before every known season (AC 2's last case, where `spring` and `playoffs` are `null` themselves); read from the calendars S128 already reads, so they cost no MLB standings request; `table` is a `StandingsSnapshot` with S128's meaning of `phase`, `season` and `date`, present only for a phase the request included (AC 3).
