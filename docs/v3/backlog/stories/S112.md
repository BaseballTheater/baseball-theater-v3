**Gap:** Local development has a handful of committed games. The owner, 2026-11-02: *"Seed the database with the final 1 month of the season and postseason (hydrate it, save it to a file, load it into memory on dev start) and include a command to refresh the seed data with parameters for the start and end dates of the data to seed."* The full range (about 450 games with plays, roughly 300 MB raw, 45 MB gzipped) can't be bundled into the local Worker or committed, so, asked how dev should load it, the owner chose a git-ignored seed file loaded into the local Postgres (S51), *"along with documentation for how to produce the file by running a command"*. Added by the owner (2026-11-02).

**Impact:** Before S112, local Baseball Theater showed a few recorded games. After it, it holds the end of the season and the whole postseason, real and complete, and one command refreshes any date range.

**Source:** Pillar: Delightful — developers too: one command gives local Baseball Theater real end-of-season and postseason data, with no serious setup (as S51 cites it). Asked whether S112 may cite Delightful, and S113 and S114 Dependable. Approved by owner 2026-11-02: "yes those are good pillars to use"

**Acceptance criteria** (checks `scripts/verify-S112.sh` performs)

1. `pnpm seed:refresh --start=YYYY-MM-DD --end=YYYY-MM-DD` fetches every schedule day in the range and each of its games, hydrated (snapshot with plays, content, play metrics), through `HttpMlbStatsClient`, and writes one gzipped seed file at a git-ignored path (`.gitignore` names it); with no dates it uses the most recent season's last month of the regular season through its last postseason game (S111's season calendar). A test runs it against a recorded `fetch` stand-in and checks the file's days and games.
2. On start, `pnpm dev` loads the seed file into the local Postgres through the repositories (version-guarded upserts, so loading twice changes nothing: test on PGlite); without a seed file it starts as before and prints the command that makes one.
3. The dev composition serves seeded days and games from the store without asking MLB again (a refresh-on-read of a seeded, final game finds it fresh; test), so local dev needs no network once seeded.
4. `README.md` documents producing the seed (the command, its defaults, size and time to expect, where the file goes) and that CI and `pnpm verify` never use it.
5. No test or `pnpm verify` reads the seed file or the network (grep: tests use recorded stand-ins).
6. This file's S112 **Status** (story heading and top table) is `done`.
