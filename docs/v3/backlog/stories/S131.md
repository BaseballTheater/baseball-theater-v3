**Gap:** The owner wants a fan-facing change log for every release, its bucketing approved by them each time (owner, 2026-11-08: *"The change log and bucketing need to be manually approved by me for each release"*; asked how, *"Draft, you approve in session"*). Today the only record is `CHANGELOG.md`, written per story for anyone, including dev-only changes, and nothing ties a release to an approved summary: a release can publish with no notes at all, and no build knows which release it is.

**Impact:** Before S131, a release went out with no fan-facing summary and nobody had signed off on how its changes were described. S131 impact: every release has one short list of what changed for fans — big additions, their own items, and one "fixes and polish" line — that the owner approved before it went out, and production refuses a release without it.

**Source:** Feature: Update / change log UX

**Acceptance criteria** (checks `scripts/verify-S131.sh` performs)

1. `packages/domain` defines a release's notes (`ReleaseNotes`) and one parser for them (`parseReleaseNotes`): `version` (`vMAJOR.MINOR.PATCH`, each part a number with no leading zero, so `v3.01.0` is rejected rather than read as `v3.1.0`); an optional `date` (a real calendar date, `isCalendarDate`); `headline`, the really big additions, which the change log page shows under its gold "Major Feature" header (S133, S134; the update notice shows no addition since the owner's answers of 2026-11-10, evening) (each a title and one sentence); `items`, every change that gets its own entry (each a `kind` — `feature`, `enhancement` or `fix` (owner, 2026-11-10: *"maybe feature, enhancement, bug fix, are the big three"*) — a title and one sentence); an optional `fixesAndPolish`, the one sentence that stands for all the minor fixes; and an optional `approval` (a real calendar date and the owner's words, quoted). An entry is in `headline` or `items`, never both. The parser returns the notes or every problem it found, by field (unit tests: a valid file; a bad version, including a leading zero; an impossible date; an unknown `kind`; an empty title or sentence; an approval with no quote; the same title in `headline` and `items`; notes with nothing in any bucket, which are rejected; notes holding only `fixesAndPolish`, which are valid, as a fixes-only release's are; `v3.0.0`, whose zero parts are valid).
2. `packages/domain` has one exported check of a release version (`parseReleaseVersion`, the same rules as AC 1's `version`; `parseReleaseNotes` uses it), one comparison of release versions (`compareReleaseVersions`, numeric per part, so `v3.10.0` is newer than `v3.9.0`) and one answer to "which release is this build" (`currentRelease`: the newest **approved** notes among those given, ignoring drafts) (unit tests, including `parseReleaseVersion` on `v3.01.0`, `3.1.0` and an empty string, `v3.10.0` newer than `v3.9.0`, a newer draft that is ignored and no approved notes at all).
3. `pnpm release:check <version>` exits 0 only when `releases/<version>.json` exists, parses (AC 1), is approved (date and a non-empty quote) and its `version` matches the file name; otherwise it exits nonzero and prints each problem (tests over temporary directories: missing file, draft, mismatched version, valid).
4. The production deploy job (`.github/workflows/deploy.yml`, `production`) runs `pnpm release:check` with the release's tag (`github.event.release.tag_name`) after its Install step and before it builds anything, so a release whose notes aren't approved in the tagged commit fails before deploying (grep, read inside the `production:` job's block only: the file has a "Build the web app" step in four jobs, so a whole-file grep would pass with the check in the wrong one).
5. `CLAUDE.md`'s release rule says the coordinator drafts `releases/<version>.json` from the milestone's merged pull requests' `CHANGELOG.md` entries, bucketed as FEATURES' change log page says (big additions in `headline`; very impactful fixes, new settings, new features and significant design changes as their own `items`, each a feature, an enhancement or a bug fix; minor fixes and polish in `fixesAndPolish`), shows the draft to the owner, writes the owner's in-session approval into `approval` quoted, lands it in `stage` through a pull request, and publishes only a commit where `pnpm release:check <version>` exits 0 and whose milestone pull requests the notes all describe (one that merged into `stage` after the draft is either drafted in and re-approved, or left out by releasing the commit where the notes landed and moving it to the next milestone); never writing an approval the owner didn't give in the current session, except AC 6's copies; and it replaces the sentence that held each release's fan-facing notes in its GitHub Release until S131 (grep).
6. `releases/` holds a notes file for every release published from v3.1.0 until S131, each copied from its GitHub Release notes, whose `approval` quotes the owner's approval as recorded when it was published, or, if none was recorded, the owner's approval of that file given in S131's session (asked, never assumed). The grader checks offline only, so it still holds when re-verified at the shipping commit: `releases/v3.1.0.json` exists and `pnpm release:check` exits 0 for every file in `releases/`. Which releases were published before S131 is listed by the coordinator at commit time (`gh api repos/<repo>/releases --jq '.[] | select(.draft | not) | .tag_name'`; REST, since `gh release list` uses GraphQL, which Claude Code sessions can't reach) and recorded in the story's ledger notes. Without these, every build after S131 would have no approved notes, so `currentRelease` would be null and the page (S134) would start empty although v3.1.0 is live.
