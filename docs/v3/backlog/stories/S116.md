**Gap:** The only sign-in BT has is the local dev stand-in (`Bearer dev:<uid>`), and S114 AC 7 turns it off on every deployed site, so nobody can sign in on staging or production. ADR-019 chose Logto Cloud for sign-in (email, passwordless, no passkeys at launch) behind the identity ports that already exist: `IdentityProvider.completeSignIn` takes a Logto ID token, `IdentityAdmin` lists, disables and deletes accounts, and the web `Session.signIn()` is the one entry point the header's "Sign in" calls (`web/src/session/session.ts`). No adapter implements them for Logto yet. Inserted by the owner, 2026-11-05 (asked whether a Logto story should be sliced to land before the production release: *"Yes it is ok re: logto, and add a logto story ahead of production"*).

**Impact:** Before S116, the deployed Baseball Theater had no way to sign in, so settings and account features only worked on a developer's machine. S116 impact: fans sign in on the real site with a one-time code sent to their email, and Baseball Theater can launch with accounts.

**Source:** Feature: Modern membership

**Acceptance criteria** (checks `scripts/verify-S116.sh` performs)

1. A Logto `IdentityProvider` adapter under `functions/src/adapters/` completes a sign-in from a Logto ID token as the port describes: it checks the signature against the tenant's JWKS (`<endpoint>/oidc/jwks`), that the issuer is `<endpoint>/oidc`, that the audience is the web app's ID and that the token hasn't expired, and returns `{ provider: "logto", subject: sub, email, emailVerified: email_verified }`. It refuses a bad signature, issuer, audience, an expired token, and a token without an email (tests sign tokens with a locally made key and serve its JWKS from a fetch stand-in; no network).
2. The Worker offers the Logto provider in every environment whose `vars` name `LOGTO_ENDPOINT` and `LOGTO_APP_ID`, and the dev provider only where S114 AC 7 allows it: a valid Logto ID token signs in through a sign-in route this story adds to the API route table (so `openapi/bt-api.v1.json` lists it, regenerated by `pnpm api:spec`), which calls the provider's `completeSignIn` and the existing `signIn` and returns BT's own session token, and a `dev:` token is refused (workerd test). (Corrected by the 2026-11-05 backlog review: HEAD has no sign-in route; the dev sign-in signs in on every request through `authenticate`, `functions/src/services/accounts.ts:107`.)
3. The web app's `AuthClient` (ADR-019) is the only module that imports Logto's browser SDK (grep). On a deployed site `Session.signIn()` sends the user to Logto's hosted sign-in with the `email` scope, a callback route finishes it and hands the ID token to BT once, and `signOut()` ends both BT's session and Logto's; locally the dev sign-in is unchanged (RTL tests with a stand-in client). Every `signIn()` asks Logto for a fresh sign-in (`prompt=login`), so Settings' "Sign in again" before deleting an account sends a new emailed code, as ADR-028's recent-sign-in check requires, rather than coming back on Logto's own session (RTL test: the stand-in client is asked with `prompt: "login"`). Every browser key Logto's SDK writes goes through `web/src/storage/` (labeled personal in `STORAGE_KEYS`) and is gone after `signOut()` and after account deletion; `bt/no-browser-storage` is not disabled anywhere (RTL test reads `localStorage` and `sessionStorage` after sign-out; grep). (Added by the 2026-11-05 backlog review.)
4. A Logto `IdentityAdmin` adapter lists, disables (`PATCH /api/users/{id}/is-suspended`) and deletes (`DELETE /api/users/{id}`) accounts through the Management API, with machine-to-machine credentials from Worker secrets; account deletion (S77) deletes a user's Logto account through it (tests with a fetch stand-in).
5. The Logto endpoint and app ID are `vars` per environment in `wrangler.jsonc`; the machine-to-machine secret is a Worker secret pushed from GitHub secrets on every deploy (S114 AC 8), never the repo (grep). Every deploy sets the web app's redirect and sign-out URIs for its environment through the Management API from constants in the repo (and the email one-time-code sign-in settings, if the API exposes them), idempotently, so no address is entered in Logto's console by hand (owner, 2026-11-05: "Agreed on all points"; workflow check, and a test with a fetch stand-in runs it twice). `README.md` documents the owner's Logto setup that stays manual: the tenant, the single-page app (its URIs come from the deploy), email sign-in with a one-time code (and a link in the same email if Logto offers it), and the machine-to-machine app with Management API access. Any step a workflow performs is idempotent (owner, 2026-11-05: "All the bootstrapping should be like that").

**Notes (2026-11-05 backlog review, scope limited by the owner to S114 and S116):**

- **No sign-in route at HEAD (AC 2 corrected).** The API route table (`functions/src/handlers/api.ts`) has `/api/v1/me…` routes and none that takes a credential; the web's dev sign-in stores `dev:test-user` as the bearer (`web/src/session/SessionProvider.tsx` `signIn`) and the server signs it in on every request (`authenticate`). Logto needs a route that takes the ID token once and answers with BT's session token, which the web stores as it stores the dev token today (`web/src/session/token.ts`). A new route changes the committed spec, so `openapi/bt-api.v1.json` joins the fence; it adds an operation, which the breaking-change gate allows.
- **AC 5 runs in the deploy workflow**, so `.github/workflows/` joins the fence. The owner's agreement to AC 5 ("Agreed on all points") is this story's go-ahead to change the deploy workflow S114 writes, for the Logto steps only (CLAUDE.md). Agents never run a production deploy.
- **Fresh sign-in before deletion (AC 3).** S77's deletion checks the session is under 10 minutes old (`RECENT_SIGN_IN_SECONDS`, `functions/src/services/account-deletion.ts:23`) and Settings' "Sign in again" calls the same `Session.signIn()` (`web/src/pages/settings/AccountData.tsx:207`). Without `prompt=login`, Logto would hand back a new ID token from its own session cookie with no emailed code, which ADR-028 rules out ("a fresh emailed code through Logto").
- **Logto's browser keys (ADR-028 personal-data sweep).** The inventory's Browser row covers what `web/src/storage/` stores, and `bt/no-browser-storage` forbids storage access elsewhere; Logto's browser SDK keeps its own tokens in `localStorage`/`sessionStorage` unless it is given a storage adapter. Give it one over `web/src/storage/`.
- **One copy of the Logto endpoint and app ID.** AC 5 puts them in each environment's `vars`; the web app should read them from the Worker (or have the deploy pass the same values to the build) rather than keep a second copy that can drift.
- **The callback route draws nothing new.** It finishes the hand-off and returns to where sign-in started, showing the app's existing loading state; if it turns out to need a screen of its own, stop and ask (rule 18).
- **Management API access (AC 4, AC 5):** the machine-to-machine app gets a token from `<endpoint>/oidc/token` with the client-credentials grant for the tenant's Management API resource; check the resource indicator against Logto's docs when the story starts.
- **Preview addresses.** Each preview has its own address, so AC 5's "for its environment" adds that PR's redirect and sign-out URIs on each preview deploy; asked of the owner with this review whether previews should offer Logto sign-in at all.
