**Gap:** The only sign-in BT has is the local dev stand-in (`Bearer dev:<uid>`), and S114 AC 7 turns it off on every deployed site, so nobody can sign in on staging or production. ADR-019 chose Logto Cloud for sign-in (email, passwordless, no passkeys at launch) behind the identity ports that already exist: `IdentityProvider.completeSignIn` takes a Logto ID token, `IdentityAdmin` lists, disables and deletes accounts, and the web `Session.signIn()` is the one entry point the header's "Sign in" calls (`web/src/session/session.ts`). No adapter implements them for Logto yet. Inserted by the owner, 2026-11-05 (asked whether a Logto story should be sliced to land before the production release: *"Yes it is ok re: logto, and add a logto story ahead of production"*).

**Impact:** Before S116, the deployed Baseball Theater had no way to sign in, so settings and account features only worked on a developer's machine. S116 impact: fans sign in on the real site with a one-time code sent to their email, and Baseball Theater can launch with accounts.

**Source:** Feature: Modern membership

**Acceptance criteria** (checks `scripts/verify-S116.sh` performs)

1. A Logto `IdentityProvider` adapter under `functions/src/adapters/` completes a sign-in from a Logto ID token as the port describes: it checks the signature against the tenant's JWKS (`<endpoint>/oidc/jwks`), that the issuer is `<endpoint>/oidc`, that the audience is the web app's ID and that the token hasn't expired, and returns `{ provider: "logto", subject: sub, email, emailVerified: email_verified }`. It refuses a bad signature, issuer, audience, an expired token, and a token without an email (tests sign tokens with a locally made key and serve its JWKS from a fetch stand-in; no network).
2. The Worker offers the Logto provider in every environment whose `vars` name `LOGTO_ENDPOINT` and `LOGTO_APP_ID`, and the dev provider only where S114 AC 7 allows it: a valid Logto ID token signs in through a sign-in route this story adds to the API route table (so `openapi/bt-api.v1.json` lists it, regenerated by `pnpm api:spec`), which calls the provider's `completeSignIn` and the existing `signIn` and returns BT's own session token, and a `dev:` token is refused (workerd test). (Corrected by the 2026-11-05 backlog review: HEAD has no sign-in route; the dev sign-in signs in on every request through `authenticate`, `functions/src/services/accounts.ts:107`.)
3. The web app's `AuthClient` (ADR-019) is the only module that imports Logto's browser SDK (grep). On a deployed site `Session.signIn()` sends the user to Logto's hosted sign-in with the `email` scope, a callback route finishes it and hands the ID token to BT once, and `signOut()` ends both BT's session and Logto's; locally the dev sign-in is unchanged (RTL tests with a stand-in client). Every `signIn()` asks Logto for a fresh sign-in (`prompt=login`), so Settings' "Sign in again" before deleting an account sends a new emailed code, as ADR-028's recent-sign-in check requires, rather than coming back on Logto's own session (RTL test: the stand-in client is asked with `prompt: "login"`). Every browser key Logto's SDK writes goes through `web/src/storage/` (labeled personal in `STORAGE_KEYS`) and is gone after `signOut()` and after account deletion; `bt/no-browser-storage` is not disabled anywhere (RTL test reads `localStorage` and `sessionStorage` after sign-out; grep). (Added by the 2026-11-05 backlog review.)
4. A Logto `IdentityAdmin` adapter lists, disables (`PATCH /api/users/{id}/is-suspended`) and deletes (`DELETE /api/users/{id}`) accounts through the Management API, with machine-to-machine credentials from Worker secrets; account deletion (S77) deletes a user's Logto account through it (tests with a fetch stand-in). Only production has the machine-to-machine app (owner, 2026-11-06/07, asked whether the Logto plan includes one machine-to-machine app at no extra cost and the $8 is only for a second: "Yes"), so its secret is a production Worker secret only, and the Worker composes the Logto admin only where that secret is set; staging has no Logto admin, and deleting an account there still succeeds and removes staging's rows (test).
5. The Logto endpoint and app ID are `vars` per environment in `wrangler.jsonc`; the machine-to-machine secret is a Worker secret pushed from GitHub secrets on every production deploy (S114 AC 8), never the repo (grep). Staging never uses production's Logto tenant: it signs in through a separate staging Logto tenant or a fake identity shim (owner, 2026-11-06: "We will use a staging one or a fake shim"), so staging's accounts are test accounts and the staging branch never holds a fan's data (S114 AC 9). Previews offer no Logto sign-in (owner, 2026-11-06/07, asked "Are you okay with PR previews not having sign-in, so staging is where you test it?": "Yes", superseding 2026-11-05's "Yes to Logto" for previews): `env.preview` names no Logto vars, and the `preview` and `preview-teardown` jobs read no Logto value (grep and workflow check). (Added applying the owner's answer to the 2026-11-06 backlog review; narrowed by the owner's answers of 2026-11-06/07.) Every production deploy sets production's web app redirect and sign-out URIs through the Management API from constants in the repo (and the email one-time-code sign-in settings, if the API exposes them), idempotently, so no production address is entered in Logto's console by hand (owner, 2026-11-05: "Agreed on all points"; workflow check: only the `production` job runs it, and a test with a fetch stand-in runs it twice). `README.md` documents the owner's Logto setup that stays manual: the production tenant at `auth.baseball.theater` and the staging tenant (or, if the shim is used, that staging has no tenant), each one's single-page app, email sign-in with a one-time code (and a link in the same email if Logto offers it), production's one machine-to-machine app with Management API access, and, because staging has no machine-to-machine app, staging's redirect and sign-out URIs entered once by hand in its console.
