**Gap:** Staging has no sign-in. S116 offers Logto only where an env's vars name a tenant (`logtoSignIn`, `functions/src/worker-app.ts:181`), only production does, and staging must never use production's tenant (owner, 2026-11-06: *"We will use a staging one or a fake shim"*). So `stage.baseball.theater/api/v1/sign-in` answers `{"logto":null}`, and the header's "Sign in" does nothing there at all (`SessionProvider.tsx:126`: a production build without Logto returns). The owner clicked it on staging on 2026-11-10 (*"I clicked Sign in and nothing happened"*) and chose the shim (owner, 2026-11-10: *"Can we make it a session-only shim where clicking Sign In gives me a cookie that is valid but which uses a mock version?"*). Their concern is that the account API works behind it (owner, 2026-11-10: *"What I wanted to make sure of was that other API stuff wouldn't break, like if I try to change my account settings but don't have any account"*). Asked whether every click signs in as one shared test account and whether a site with no sign-in at all (pull request previews) hides the button, the owner answered *"yeah, plan this story and move it up to the top priority."* The same dead button is on every preview, which offers no sign-in by design (owner, 2026-11-07: "Yes", to previews without sign-in).

**Impact:** Before S143, nobody could sign in on the staging site: the Sign in button did nothing, so nothing that needs an account (Settings, favorites, deleting your account) could be tried there before a release. S143 impact: on staging, Sign in signs you straight in as one shared test account, with no emailed code (the account has an email address of its own, as every account does), and everything an account does works as it will on the real site. On a test site with no sign-in at all, the button is gone instead of doing nothing.

**Notes:**

- **"Cookie" is BT's session token.** BT's session isn't a cookie: `POST /api/v1/sign-in` answers a signed session token that the web app keeps in browser storage and sends as a bearer (`setSessionToken`, `web/src/session/token.ts`; S59). The owner's "a cookie that is valid" is that token, a real one signed with staging's `BT_SESSION_KEY`; only who vouches for the sign-in is mocked. Its expiry is the session's usual 7 days.
- **Why one shared account.** The owner agreed to one shared test account rather than a new one per click, so settings carry over between visits. Staging is public, so anyone who clicks Sign in there lands in that same account and can change it, or delete it, after which the next sign-in starts a new one with house-default settings (AC 4). That is acceptable because staging holds no fan's data (S114 AC 9): its accounts are test accounts in staging's own database (S116's 2026-11-06 notes), and the copy of production's baseball data (S117) never copies accounts.
- **How it differs from the dev sign-in (S116's 2026-11-06 note asked for this before any shim).** The dev sign-in (`Bearer dev:<uid>`, `DevIdentityProvider`) lets any request act as any uid it names, with no session issued, and stays local only (S114 AC 7). The mock is a provider like Logto: one fixed credential, one fixed account, traded once at `POST /api/v1/sign-in` for an ordinary BT session, and wired only on staging. Nothing accepts a `dev:` token on a deployed site afterwards.
- **Where it fits in the code.** `AuthDeps` (`functions/src/services/accounts.ts:16`) gains the provider beside `logto`, and `completeProviderSignIn` (`:135`, which answers null today when no Logto is wired, hence the 404) sends the mock credential to it when it is wired. `createWorkerApp` (`functions/src/worker-app.ts:113`) wires it next to `logtoSignIn`. The web side's loader is `deployedAuthClient` (`web/src/session/SessionProvider.tsx:71`) with `loadAuthClient` (`web/src/session/AuthClient.ts:160`), which reads `fetchSignInConfig()`, and `exchangeIdToken` already does the hand-off (`SessionProvider.tsx:142`). The header's button is in `web/src/layout/AppHeader.tsx:34`.
- **No design story.** The signed-in and signed-out headers are ratified (shell-scoreboard A2) and look the same on staging. Hiding the button on previews only removes it from a test site no fan sees, so nothing new is drawn (rule 18). The owner approved it in words (*"yeah, …"*, above).
- **Patreon isn't mocked.** Linking Patreon goes out to Patreon itself, which this story doesn't stand in for; it stays as it is on staging.
