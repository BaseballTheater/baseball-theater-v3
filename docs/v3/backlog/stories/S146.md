**Gap:** Whether staging deploys is decided by a path list: `scripts/ci-changes.sh` calls any `*.md`, `docs/` or `.claude/` change docs and everything else code (owner, 2026-11-07: *"Things like this shouldn't trigger CI."*; staging stopped deploying docs-only pushes on 2026-11-11). A list says nothing about what the build actually reads. A change to a script, a test or a fixture the app never bundles still rebuilds, migrates and redeploys staging, and the list must be kept by hand. The owner asked for the decision to come from the build's inputs instead (2026-11-11): *"ultimately it'd be nice if this used some kind of hashing or something rather than directory allow/blocklists … What I'd like is for something to check the inputs to the build at build time or prior to it (ideal) or for the build output hash to be compared to the last deployed output hash (less ideal, only works if the build output is deterministically identical with identical inputs)"*, then *"yeah, I like your plan"* to recording what the build reads and checking those files' hashes before the next build.

**Impact:** Before S146, staging rebuilt and redeployed after almost any change, even one that changed nothing the site is built from (a test, a script, a fixture), and which changes counted was a hand-kept list. After S146, each deploy records exactly which files went into it, and the next one skips the build and the deploy when none of them changed, so staging only redeploys when what it serves could actually be different.

**Source:** Pillar: Delightful — deploys run only when what they build from changed, so changes reach staging without churn from edits that change nothing it serves; the same reason S89 cites for faster checks. Asked "Can the input-hash story cite the Delightful pillar (as S89 did), or Dependable?" Approved by owner 2026-11-11: "delightful"

**Acceptance criteria** (checks `scripts/verify-S146.sh` performs)

1. **Recording the inputs.** A `pnpm build:inputs record <out>` command (its code under `functions/src/deploy/`) writes, after a build, a JSON record of every file that build read, each with its git blob hash at the built commit:
    - every module the web build bundled, taken from Vite's own module graph (a plugin in `web/vite.config.ts` that writes the list it reports, never a hand-kept list of folders);
    - every module the Worker bundle read, taken from the bundler's own metafile (`wrangler deploy --dry-run --metafile`);
    - a short, named list of inputs outside those graphs: `pnpm-lock.yaml`, every workspace `package.json`, `.nvmrc`, `wrangler.jsonc`, the TypeScript, Vite and Wrangler configs and every repository file those configs import (`web/vite.config.ts` imports `web/src/pwa/options.ts`), `web/index.html`, every file under `web/public/` (copied, not imported), every migration the deploy applies, and `.github/workflows/deploy.yml` with the scripts its deploy steps run.

   Files under `node_modules/` and virtual modules (ids starting `\0` or `virtual:`) have no git blob and are left out: `pnpm-lock.yaml` stands for the dependencies. Unit tests (`functions/src/deploy/`) show, against a fixture repository: a file the build imports is recorded; a Markdown file and a test file are not; a file under `web/public/`, a migration, `web/index.html` and a file a config imports are; a `node_modules` path and a virtual module are left out without failing.
2. **Checking the inputs.** The check runs with plain `node` and no installed dependencies (Node 24 runs TypeScript with only `node:` imports), so it can run before `pnpm install`: `node functions/src/deploy/build-inputs.ts check <record>` (also `pnpm build:inputs check <record>`) exits 0 and prints `unchanged` only when the record parses and every file it lists has the same blob hash at HEAD. It exits nonzero, naming the first difference, for: no record, a record it can't parse, a listed file whose hash changed, a listed file that was deleted, and a record made by a different version of the command. Unit tests cover each case. A new source file can only enter a build through an import added to a recorded file, so that edit changes a recorded hash; a test shows adding an import to a recorded file makes `check` fail.
3. **Deploying from it.** In `.github/workflows/deploy.yml`, the `staging` job and the `preview` job each fetch the record of their environment's last successful deploy before installing or building (the jobs gain `actions: read` if the record is an Actions artifact), and skip install, build, migrations and deploy when `check` prints `unchanged`. This is an extra skip inside the jobs: the docs-only gate and its law P11 test (`scripts/backlog-vault/ci-law.test.ts`, outside this story's fence) stay as they are, so verify still runs only for code. A record is stored only after its deploy step succeeds, so a failed or cancelled deploy never leaves one, and it names the commit it deployed: staging deploys when the commit it serves (`bt-commit.txt`) isn't that record's commit, so a `wrangler rollback` or an older run landing last is never left in place. Staging's served-commit check still runs, so an older run never deploys over a newer one. A skipped preview still posts its comment, saying the preview from the recorded commit still serves this one. A record is only trusted while its Worker exists: `preview-teardown` deletes the pull request's record along with its Worker, and a `reopened` event always deploys, so a reopened pull request never gets a "still serves" comment for a deleted preview. A manual run of Deploy for `stage` with a `force` input deploys staging whatever the record says (for a rotated secret or variable, which changes no file), and README names it. The `production` job always deploys. A test in `functions/src/deploy/` reads `deploy.yml` and pins all of this.
4. **Documented.** README's deploy section says a staging or preview deploy is skipped when the recorded inputs of its last successful deploy are unchanged, and where the record is kept; `deploy.yml`'s comments say the same, and both name the input check where they say what decides a staging deploy: grep finds `build:inputs` in `deploy.yml`'s staging and preview jobs and in README's Staging bullet. A docs-only push still deploys nothing, so the existing wording about it (`deploy.yml`, README, `wrangler.jsonc`) stays true and isn't edited.

**Notes:**

- **Why inputs, not output hashes.** The owner ranked hashing the build output below checking its inputs, since it "only works if the build output is deterministically identical with identical inputs", and it still pays for every build. Vite's output isn't promised to be byte-identical across runs.
- **What keeps the list honest.** Only the short list in AC 1's third bullet is kept by hand: things the bundlers never see. Everything the app imports comes from the bundlers' own graphs. If a deploy step starts reading a new kind of file, that list gains it in the same change.
- **Where the record lives.** Not prescribed. A GitHub Actions artifact per environment (`build-inputs-staging`, `build-inputs-preview-<n>`) found through the Actions API, or a file served beside `bt-commit.txt`, both work. Whichever is chosen must not be readable as "unchanged" when the last deploy failed, or after its Worker was deleted (AC 3).
- **Previews.** A preview Worker is per pull request, so its record is per pull request too; the first push to a pull request always deploys.
- **2026-11-11 pre-PR review.** AC 3 first said staging's decision would no longer read the path list, which would have meant dropping the gate law P11's test pins, a file outside the fence and a law the owner owns; the input check is now an extra skip inside the jobs. It also added: the check running before install (AC 2), `node_modules`, virtual modules, `index.html` and config imports (AC 1), a deploy when staging serves another commit or by a `force` run (AC 3), and AC 4's grep patterns.
