**Gap:** MLB lists the uniform assets each team wore in a game; BT doesn't keep them (owner, 2026-10-30: *"Also add stories to ingest all of this extra data."*).

**Impact:** Before S101, BT didn't know what either team wore. S101 impact: BT keeps each game's uniforms ("Marlins Home White Jersey"), ready for a view to use.

**Source:** Feature: More MLB game data

**Scope files:** `fixtures/`, `packages/mlb-api/src/`, `packages/ports/src/`, `packages/domain/src/`, `functions/src/`, `functions/vitest.config.ts`, `openapi/`, `web/src/api/generated/`, `docs/v3/BACKLOG.md`, `docs/v3/backlog/`, `docs/v3/AUDIT.md`, `CHANGELOG.md`

**Work**

0. Write `scripts/verify-S101.sh` meeting the [Verify-script contract](#verify-script-contract). Run it against current HEAD and show the nonzero exit **before** building (rule 9).

**Acceptance criteria** (checks `scripts/verify-S101.sh` performs)

1. `fixtures/raw/uniforms-823823.json` holds MLB's response to `https://statsapi.mlb.com/api/v1/uniforms/game?gamePks={gamePk}` for 823823, recorded once with `BT_USE_LIVE_MLB=1` and committed; tests and local dev read it, never the network.
2. `packages/mlb-api` types the payload as named interfaces split by purpose and parses it with zod; a parse test runs on the recording, and `pnpm mlb:scan-drift` diffs it against the parser like the other payloads.
3. `MlbStatsClient` gains `fetchGameUniforms(gamePk)`, implemented by the fixture adapter and the HTTP adapter; ingest owns the call (ADR-002): no web code fetches it.
4. A mapper in `functions/src/mappers/` projects it into BT's own shape, `GameSnapshot.uniforms`, added to the game payload additively (regeneration test; `pnpm api:breaking` exits 0). Per side, each asset's code, text and type (jersey, pants, cap…); on 823823 the home side includes "Marlins Home White Jersey" (test).
5. The source is optional: when the call fails or returns nothing, the field is absent and the game is served as before (test).
6. This file's S101 **Status** (story heading and top table) is `done`.
