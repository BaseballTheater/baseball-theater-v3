**Gap:** S114 gives staging (and the previews that share it) a schema-only Neon branch filled by `pnpm db:migrate`, so its tables start empty: the scoreboard, games and videos fill in only as fans visit and ingest pulls from MLB. The owner wants staging to hold production's baseball data and none of its fans' data (2026-11-05: "No user data, copied baseball data"), copied as its own step that is run by hand, not on every deploy, so whatever someone is iterating on isn't overwritten (2026-11-05, asked whether the copy should be its own story: "Its own story, before production launch, but it should be a manual step (to allow for local iteration not getting stomped)").

**Impact:** Before S117, staging started empty and only filled in as people browsed it. S117 impact: when the owner asks, staging gets every game, schedule and video production has, with no fan's account or settings, and nothing overwrites it in between.

**Source:** Pillar: Delightful — developers too: staging that already holds production's games, schedules and videos makes testing on `stage.baseball.theater` much faster. Asked whether S114's Dependable approval covers S117, or it should cite something else. Approved by owner 2026-11-06: "Delightful, bc it makes testing much faster in stage"

**Acceptance criteria** (checks `scripts/verify-S117.sh` performs)

1. One command copies production's baseball data into a target database: only the Postgres tables `DATA_CLASSIFICATION` (`functions/src/services/data-classification.ts`) labels `none` are read and written, so no personal or deletion-log (`retained`) row is ever written to the target, not even for a moment (a test copies between two PGlite databases holding both kinds of row and finds every baseball row copied and every personal table and the deletion log empty in the target).
2. It's idempotent: running it again changes nothing, and rows already newer in the target are kept through the same version-guarded writes as ingest (ADR-022), so the copy never rolls staging back (test: copy twice; and a target row with a higher version survives).
3. It only adds to staging, never takes away, because staging can run ahead of production in both schema and data (owner, 2026-11-05: "if I make changes to data and schemas that's different from production, it'll need to have data in staging that isn't present in production"). It never deletes, truncates or drops anything in the target. Rows that exist only in staging stay as they are. It copies only the columns both sides have, so a table or column that only staging has (from a migration production hasn't had yet) is left untouched, and a column only production has is skipped. It migrates the target first and never migrates or changes production (test: a target one migration ahead, with an extra column and a staging-only row, keeps both after the copy, and gets production's rows).
4. It runs only when someone asks: a manual trigger (a `workflow_dispatch` workflow with the staging target, or a command given both connection strings), never a step of any deploy, PR or push workflow (workflow check; grep).
5. It refuses to write to production: the target can't be the production branch or `bt-production` (test).
6. `README.md` says what it copies and what it never does, how to run it, and that deploys never run it.
7. This file's S117 **Status** (story heading and top table) is `done`.
